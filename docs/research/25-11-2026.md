# HomeRadar — техническое исследование

**Дата:** 25-11-2026  
**Область:** базовая реализация Android Wi-Fi acquisition, camera/IMU tracking, Rust core и Kotlin bridge.

## 1. Текущая концепция

HomeRadar строит не план помещения, а траекторию движения смартфона в локальной системе координат. Wi-Fi-наблюдения привязываются к этой траектории по времени. Основные артефакты сессии:

- линия пройденного пути;
- временные метки и качество каждой позиции;
- Wi-Fi-измерения с исходным временем измерения;
- точки измерений и отдельные слои диапазонов;
- тепловая карта с плотностью выборки и уровнем уверенности;
- исходные данные, позволяющие повторно обработать сессию.

Обязательное распознавание стен, комнат, дверей и построение floorplan исключены из базового сценария.

## 2. Android Wi-Fi scanning

Официальный обзор Android Wi-Fi scanning:
https://developer.android.com/develop/connectivity/wifi/wifi-scan

Ключевые выводы:

- На Android 10+ приложение может получать broadcast о завершении полного Wi-Fi scan, инициированного системой или другим приложением, и пассивно слушать обновления.
- `getScanResults()` возвращает последние доступные результаты. Если сканирование не завершилось успешно, это могут быть старые результаты.
- Ограничения частоты активного сканирования зависят от версии Android. Документация описывает для Android 9+ до четырёх сканирований за две минуты на foreground-приложение и одно сканирование за 30 минут для всех background-приложений.
- `WifiManager.startScan()` устарел начиная с API 28; не строить архитектуру вокруг предположения, что приложение может запускать непрерывные сканирования.
- Для получения результатов могут требоваться разрешения Wi-Fi/геолокации и включённые системные службы; фактические требования зависят от Android API и target SDK.

**Решение для HomeRadar:** реализовать сбор доступных scan results и событий обновления, сохранять platform timestamp и receive timestamp отдельно, вычислять возраст результата и явно помечать stale/cached/failed. Wi-Fi — редкий источник измерений, а не непрерывный сенсор.

Ссылка на API:
https://developer.android.com/reference/android/net/wifi/WifiManager

## 3. Android sensor timestamps

Официальный SensorEvent API:
https://developer.android.com/reference/android/hardware/SensorEvent

Поле `SensorEvent.timestamp` выражено в наносекундах и использует монотонную временную базу, соответствующую `SystemClock.elapsedRealtimeNanos()`.

**Решение:** использовать монотонные наносекунды для синхронизации потоков сенсоров и поз. Wall-clock время хранить отдельно только для отображения и метаданных. Не синхронизировать IMU и Wi-Fi только по календарному времени.

## 4. ARCore camera pose

Официальные источники:
- Camera API: https://developers.google.com/ar/reference/java/com/google/ar/core/Camera
- TrackingState: https://developers.google.com/ar/reference/java/com/google/ar/core/TrackingState
- Session lifecycle: https://developers.google.com/ar/develop/java/session-config

ARCore предоставляет pose камеры и состояние tracking. Pose допустимо использовать как текущую только при `TrackingState.TRACKING`. При `PAUSED` качество позы может быть недостоверным; такие участки нельзя безусловно продолжать как точную линию.

**Решение:** ARCore подключать на Android-стороне как provider. В Rust передавать только нейтральные структуры pose, timestamp, tracking state и quality. ARCore остаётся необязательным; ядро не зависит от его классов и SDK.

## 5. Rust ↔ Kotlin: UniFFI

Официальный репозиторий: https://github.com/mozilla/uniffi-rs  
Документация: https://mozilla.github.io/uniffi-rs/

UniFFI генерирует Kotlin bindings для Rust-библиотеки и используется Mozilla в том числе в Firefox. На момент проверки репозиторий имеет примерно 5.1k stars и 350+ forks; лицензия проекта — MPL-2.0. В README авторы отмечают, что UniFFI используется в production, но проект ещё не достиг 1.0 и некоторые сложные интерфейсы могут меняться.

**Решение:** оставить UniFFI целевым вариантом интеграции, но не блокировать первый Rust core на FFI. Сначала определить и протестировать независимый Rust API; затем сделать отдельный небольшой Kotlin binding prototype и зафиксировать версии инструментов.

Важно: лицензия UniFFI не меняет автоматически лицензию HomeRadar; условия каждой сторонней зависимости проверяются отдельно.

## 6. UI

Официальная документация Material 3 для Compose:
https://developer.android.com/develop/ui/compose/designsystems/material3

Material 3 поддерживает темы, типографику, формы и динамические цвета Material You. Это соответствует Android-first приложению с собственным canvas для траектории.

**Решение:** Jetpack Compose + Material 3. Карта маршрута — отдельный renderer/Canvas, не попытка выразить графику только стандартными карточками UI.

## 7. Проверка сторонних проектов и зависимостей

### UniFFI
- Репозиторий: https://github.com/mozilla/uniffi-rs
- Назначение: Rust-to-Kotlin bindings.
- Популярность на дату исследования: около 5.1k stars, 350+ forks (показатели GitHub могут меняться).
- Лицензия: MPL-2.0.
- Статус: кандидат для интеграционного прототипа, не обязательная зависимость первого этапа.

### nalgebra
- Репозиторий: https://github.com/dimforge/nalgebra
- Справочная статистика: https://ml-rust.github.io/projects/nalgebra/
- В каталоге на 23-11-2026 указано около 4.8k stars, 576 forks; лицензия Apache-2.0.
- Назначение: линейная алгебра и геометрические преобразования.
- Решение: пока не добавлять. Первые типы и простые операции можно реализовать без зависимости; подключать математическую библиотеку после определения реальных требований к quaternion/матрицам/EKF.

### Базовые Rust crates
Для первого минимального ядра можно ограничиться стандартной библиотекой Rust, чтобы сократить поверхность зависимостей. Serde/SQLite/UniFFI добавлять на конкретном этапе, с фиксацией версии и проверкой лицензии.

## 8. Практическая архитектура первого прототипа

1. Rust crate с типами timestamp, 2D pose, Wi-Fi observation и quality.
2. Проверка монотонности временных меток и конечности координат.
3. Построение траектории с разрывами при больших временных промежутках.
4. Группировка наблюдений по SSID только как UI-группировка; не считать это идентификацией физического AP.
5. Пространственная агрегация RSSI по ячейкам с числом измерений; без автоматического распространения цвета на неизмеренные области.
6. Kotlin Android acquisition — отдельным этапом после проверки core.

## 9. Риски и ограничения

- Wi-Fi scan throttling и cached results ограничивают пространственную плотность измерений.
- ARCore поддерживается не на всех Android-устройствах; отслеживание может теряться.
- IMU/PDR подвержен дрейфу и не является абсолютной навигацией.
- RSSI зависит от устройства, ориентации, людей, стен, отражений и помех; это не точная дальномерная метрика.
- Пассивные сканы не раскрывают гарантированно полную топологию Mesh/backhaul.
- Heatmap должна показывать плотность измерений и не выдавать экстраполяцию за измеренный факт.

## 11. Что добавлено в начальный Rust Core после исследования

В репозитории создан стандартно-библиотечный workspace `core/` и crate `homeradar-core`.

Реализованы:
- монотонные временные метки и локальные 2D координаты;
- pose с качеством tracking;
- Wi-Fi observation с проверкой RSSI, частоты и порядка временных меток;
- грубая классификация частотных диапазонов 2.4/5/6 GHz;
- построение траектории с разрывами после больших пауз и потери tracking;
- интерполяция pose к времени Wi-Fi-наблюдения только внутри непрерывного сегмента;
- группировка SSID только для отображения;
- агрегация RSSI по ячейкам без заполнения пустых ячеек;
- синтетический пример и unit tests.

Важное ограничение: Rust toolchain в среде выполнения этой сессии отсутствует, поэтому `cargo test` здесь не запускался. Код следует проверить локально командой из `core/README.md` перед расширением Android-интеграции.

## 13. Android application bootstrap implemented

The initial Android module now uses:
- Android Gradle Plugin 9.5.2;
- Gradle 9.6.0 distribution;
- Kotlin 2.4.21 Compose compiler plugin;
- Compose BOM 2026.09.00 for the first baseline;
- Activity Compose 1.13.0;
- Core KTX 1.19.1;
- compile/target SDK 37, min SDK 26, JDK 17.

The newest Compose November 2026 release is 2026.11.01 and requires compileSdk 37.1 according to its release note. The first scaffold deliberately uses the September stable BOM while the exact SDK extension 37.1 setup is validated; this avoids silently claiming the latest BOM is already built and verified.

The Android source currently:
- requests fine-location permission before scan requests;
- listens for Wi-Fi scan-result broadcasts while the activity is started;
- can request a scan and displays Android's accepted/rejected status;
- preserves ScanResult.timestamp (microseconds since boot converted to nanoseconds) separately from receive time;
- shows stale/cached results as unconfirmed rather than fresh;
- displays SSID, BSSID, RSSI, frequency and broad band classification.

The initial app does not yet store scan sessions, track the user's position, or draw the walking route. The active scan API is deprecated and Android throttles it; passive scan-result updates are also used. No continuous scan behavior is promised.
