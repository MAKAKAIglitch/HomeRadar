# HomeRadar — выбор Wi-Fi-цели и ARCore camera mapping

**Дата проверки:** 26-11-2026  
**Область:** выбор целевой Wi-Fi-сети, ARCore camera background/pose и синхронизация Wi-Fi-замеров с маршрутом.

## 1. Повторная проверка материалов проекта

Перед изменениями изучены `docs/research/25-11-2026.md`, текущий файл `docs/research/26-11-2026.md`, `docs/ANDROID-PLATFORM.md`, `docs/ROADMAP.md`, Android manifest, Gradle-конфигурация, `WifiScanDataSource`, `MotionSensorDataSource`, `MainActivity` и Compose UI.

- В проекте уже была объявлена зависимость `com.google.ar:core:1.57.0` и optional ARCore metadata в manifest. Новую стороннюю библиотеку для AR-сессии добавлять не потребовалось.
- Ранее CameraX показывал только camera preview, а координаты маршрута строились по шагам/азимуту. Это не было AR-позиционированием.
- До этой итерации в проекте уже появился выбор SSID, фильтрация измерений по выбранной сети, локальная SQLite-сессия и экспорт/импорт `.homeradar`.
- Существующая архитектура позволила заменить источник позы, сохранив RoutePoint, историю поз, Wi-Fi-маркеры и хранение сессий.

## 2. Официальные API и платформенные ограничения

### ARCore camera frame and tracking

Официальные источники:
- ARCore `Session.update()` и `Frame`: https://developers.google.com/ar/reference/java/com/google/ar/core/Session
- ARCore `Frame.getTimestamp()` и `Frame.getCamera()`: https://developers.google.com/ar/reference/java/com/google/ar/core/Frame
- ARCore `Camera.getPose()` / tracking state: https://developers.google.com/ar/reference/java/com/google/ar/core/Camera
- ARCore session lifecycle: https://developers.google.com/ar/develop/java/session-config
- Официальные Android samples: https://github.com/google-ar/arcore-android-sdk

Выводы:
1. `Session.update()` возвращает ARCore frame и обновлённую camera pose. В blocking режиме ожидание camera image может достигать примерно 66 мс; вызов выполняется в GL/render цикле.
2. Для построения маршрута camera pose используется только при `TrackingState.TRACKING`. При `PAUSED` поза не считается пригодной для обновления траектории.
3. ARCore camera background можно выводить через OpenGL ES external OES texture, передав texture ID в `Session.setCameraTextureName()` и преобразуя координаты через `Frame.transformCoordinates2d()`.
4. `Frame.getTimestamp()` полезен для обнаружения нового кадра и пропусков, но официальная документация не фиксирует его time base. Android SDK указывает, что timestamp вероятно похож на `System.nanoTime()`; native reference уточняет вероятный `CLOCK_BOOTTIME`. Поэтому нельзя без проверки считать его полностью совместимым с каждым Android clock API.

### Android Wi-Fi scan results

Официальные источники:
- Wi-Fi scanning overview: https://developer.android.com/develop/connectivity/wifi/wifi-scan
- `WifiManager`: https://developer.android.com/reference/android/net/wifi/WifiManager
- `ScanResult.timestamp`: https://developer.android.com/reference/android/net/wifi/ScanResult#timestamp
- `SystemClock.elapsedRealtimeNanos()`: https://developer.android.com/reference/android/os/SystemClock#elapsedRealtimeNanos()

Выводы:
1. `ScanResult.timestamp` выражен в микросекундах с момента загрузки устройства; для внутренней шкалы наносекунд он умножается на 1000.
2. `SystemClock.elapsedRealtimeNanos()` — монотонные наносекунды с момента загрузки, включая время сна устройства. Это подходящая шкала для сопоставления с Wi-Fi `ScanResult.timestamp`.
3. ARCore frame timestamp имеет не гарантированную публичную time base. Поэтому текущий прототип использует `SystemClock.elapsedRealtimeNanos()` в момент обработки tracking frame как временную метку route pose. Это переводит позиции в шкалу Android elapsed-realtime, но добавляет задержку обработки относительно момента экспозиции камеры.
4. Для Android 9+ foreground-приложение ограничено четырьмя Wi-Fi scan requests за две минуты; Android 10+ сохраняет это ограничение. `startScan()` может вернуть отказ, а scan results могут быть старыми. Broadcast с `EXTRA_RESULTS_UPDATED=false` не считается новым измерением.
5. Интервал 35 секунд выбран как ограниченный foreground best-effort режим: один запрос при начале прохода, затем периодические запросы. Это не гарантирует, что каждый запрос завершится новым сканом.

### Выбор текущей Wi-Fi-сети

Официальные источники:
- `ConnectivityManager`: https://developer.android.com/reference/android/net/ConnectivityManager
- `NetworkCapabilities`: https://developer.android.com/reference/android/net/NetworkCapabilities
- `WifiInfo`: https://developer.android.com/reference/android/net/wifi/WifiInfo

На современных Android сведения активного Wi-Fi transport доступны через `ConnectivityManager` / `NetworkCapabilities.transportInfo` (`WifiInfo`); для старых версий сохраняется legacy fallback. SSID используется как выбранный фильтр сети, но не является уникальным идентификатором радио-точки: внутри выбранного SSID сохраняются отдельные BSSID.

## 3. Реализованное решение

- ARCore остаётся уже используемой optional зависимостью. CameraX удалён из Gradle и исходников, чтобы не открывать параллельно вторую camera session.
- `ArCoreCameraView` владеет одной ARCore `Session`, рисует camera background через OpenGL ES и отправляет pose только при `TrackingState.TRACKING`.
- Первое отслеживаемое AR положение становится началом локальной системы координат (0, 0). Горизонтальная плоскость ARCore X/Z переводится в локальные X/Y HomeRadar.
- Pose передаётся в MotionSensorDataSource примерно 10 раз в секунду. Wi-Fi measurement timestamp сопоставляется с историей поз; экстраполяция за пределы истории не выполняется.
- Экран перед запуском показывает подключённый SSID как цель по умолчанию. Пользователь может выбрать другой обнаруженный SSID или все сети; выбор сохраняется локально.
- Во время AR-прохода сохраняются только свежие Wi-Fi scan results выбранного SSID. Идентичность точек доступа не схлопывается: BSSID остаётся в каждой записи.
- Во время активного прохода запускаются scan requests с интервалом 35 секунд; отказ Android или stale broadcast не создаёт новые маркеры.
- При остановке/уходе Activity в фон периодические Wi-Fi requests снимаются, AR session lifecycle освобождается и локальная сессия завершается.
- Camera/video stream и полный набор IMU-событий в SQLite не записываются.

## 4. Зависимости и лицензирование

- Используется существующая зависимость `com.google.ar:core:1.57.0`; новых сторонних библиотек в этой реализации не добавлено.
- ARCore распространяется на условиях Google ARCore Additional Terms, а не MIT-лицензии HomeRadar. MIT-лицензия собственного кода не меняет условия использования ARCore.
- ARCore требует совместимого устройства и установленного Google Play Services for AR. В manifest ARCore отмечен как optional, но полноценный AR-режим требует доступности сервиса.
- CameraX удалён после перехода на ARCore-owned camera session. Отдельного camera backend в проекте больше нет.

## 5. Известные ограничения

- Сборка и запуск на физическом устройстве обязательны для проверки GLSurfaceView lifecycle, camera texture, ARCore tracking и реальной точности маршрута.
- Временная метка позы снимается при обработке frame, а не в момент экспозиции camera sensor. Задержка может влиять на точность пространственной привязки Wi-Fi-замера.
- При потере ARCore tracking маршрут не получает новую позу. Интервалы без позы нельзя представлять как точную траекторию.
- Android может отклонить scan request или вернуть cached results. Карта может быть разреженной даже при движении по помещению.
- Текущая карта — свободная 2D-траектория с RSSI-маркерами; детекция стен, комнат, дверей и построение floor plan не реализованы.
- ARCore не даёт глобальные координаты помещения. Начало каждой сессии локальное; точность зависит от visual tracking, освещения/текстуры поверхностей и relocalization.
- Автоматический выбор PDR fallback на неподдерживаемых устройствах ещё не подключён к UI.

## 6. План проверок

1. Собрать debug APK через `bash ./build.sh` или `build.bat`; отдельно проверить GitHub Actions artifact.
2. На совместимом телефоне проверить runtime CAMERA и ACCESS_FINE_LOCATION, системную геолокацию, ARCore installation prompt и живую camera background.
3. Пройти короткий маршрут с поворотом и остановкой; проверить, что route points растут только во время TRACKING, координаты меняются плавно, а distance остаётся конечным.
4. Убедиться, что выбранный SSID по умолчанию равен активному Wi-Fi, ручной выбор сохраняется после перезапуска, а фильтрация не пишет соседние SSID.
5. Проверить свежесть scan results, BSSID, RSSI и привязку marker timestamp к route history. Повторить тест с отклонённым запросом и stale broadcast.
6. Проверить pause/resume, сворачивание приложения и остановку сканирования; не должно оставаться активной камеры или периодических запросов в фоне.

**Статус на дату исследования:** код первичной интеграции добавлен в `main`. Android compile и проверка на физическом устройстве должны быть подтверждены отдельно; точность синхронизации camera pose и Wi-Fi timestamps пока не сертифицирована.
